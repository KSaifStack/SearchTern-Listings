## Scope and evidence rules

This review covers the listing generator in this repository, its published artifacts, source and snapshot handling, publication path, tests, and the product surface those artifacts support. It deliberately does **not** re-investigate the already-known tier-scoped publication failure. That failure is treated as an accepted finding and the review starts from the fix.

Evidence is labelled as one of:

- **Measured** — read from this checkout or computed from its JSON artifacts on 2026-11-10.
- **Code** — read directly from the named file and line.
- **External claim** — stated by a project README, vendor page, or API document; not independently load-tested here.
- **Hypothesis** — a proposed causal explanation or projection that needs measurement.

Limits:

- The deployed backend, its PostgreSQL schema and query plans, production secrets, and live GitHub Actions logs were not available.
- No source was re-fetched for this review. Source counts are from the committed artifacts, not a new crawl.
- The working tree has uncommitted changes to `Listings/identity.py`, `Listings/test_identity.py`, and four workflows. They are treated as **pending**, not as deployed production behavior.
- The published feed is about 31 hours old at review time (`observed_at` is `2026-11-09T07:07:34Z`), so counts can move on the next run.

## Bottom line

1. **The publication defect is still the primary blocker.** The live feed contains **13,748 rows, 55,838,379 bytes, and 100% `source=jobhive`**. The larger all-source data is fetched but not published. The root cause is already known: publication is scoped to the tiers that ran, not unioned from the eligible source snapshots.
2. **The code to fix it exists but is not in the production path.** `snapshots.py` implements success gating, TTL eligibility, precedence, and `merge()`, and the merge is unit-tested. Its own module docstring says it does not choose what a run publishes yet (`Listings/snapshots.py:1-14`). The production line still derives the feed from `listings_result` (`Listings/generate_listings.py:2196-2198`).
3. **The 15K number is stale documentation, not the live total.** The feed is 13.7K. `README.md:10,17` says 5,230; `countries/US.md:3` says 15,821 as of 2026-09-24; `docs/marketing/claims.md:34` says US 15,748. Those pages are not generated from the current feed.
4. **Data quality is now a product risk independent of row count.** `first_seen_at` is missing on **9,182 / 13,748 rows (66.8%)**; `is_remote` is true on only **841 (6.1%)** with **8,342 null (60.7%)**; `country_iso` is missing on **2,364 (17.2%)**; `direct_apply`, `employment_type`, and `seniority` are absent on every row; `visa_sponsor` is a string with only `"true"` or empty, so unknown and no are indistinguishable.
5. **Git is the wrong publication mechanism at the next size.** At 4,061.6 bytes/row, the current 55.8 MB feed reaches GitHub's 100 MB file ceiling at roughly **24.6K rows**. The snapshot audit's all-source union projects to **34,212 rows ≈ 139 MB**; the phase-4 union projects to **42,674 rows ≈ 173 MB**. A validated artifact plus a small manifest is the smallest durable fix; a growing monolithic JSON committed every run is not.
6. **Do not replace the working ingestion stack.** The source adapters, conditional HTTP cache, dedup/identity modules, closure checks, and 163 passing tests are assets. The highest-impact work is activation, atomicity, and a contract — not Dagster, Prefect, dbt, Great Expectations, Apify, or a new database.

## What is working

Keep these; they are the foundation for the fix.

- **Source diversity is real at ingestion.** The run reports 89 sources, 499,497 discovered rows, and 115,322 valid rows (`pages/health.json`). The problem is downstream selection, not a lack of inputs.
- **Conditional HTTP and bounded retries.** `http_get` uses ETag/Last-Modified caching, per-host concurrency, `Retry-After`, 429/503 handling, and a host cooldown (`Listings/readme_utils.py`). This is the right shape for polite crawling.
- **Stable identity work exists.** `Listings/identity.py` and `Listings/dedup.py` are separated and tested. The known `NA`-as-identity bug fix is in the working tree and has a regression test; it is not in the measured feed yet.
- **Closure is conservative.** `Listings/closure.py` only closes when a successfully completed board is checked; partial fetches must not imply delisting. That distinction is essential and should be preserved.
- **Snapshot policy is designed, not improvised.** `Listings/snapshots.py` has per-class TTLs, precedence, a 30% shrink gate, and a two-rejection escape hatch. These are reasonable rules and already unit-tested.
- **Reason accounting exists for the shadow publisher.** `Listings/shadow_publish.py` counts why rows were dropped, instead of publishing an unexplained total. That is the right measurement pattern.
- **The test suite is fast and meaningful.** 163 tests pass in about five seconds. The missing piece is a CI gate and end-to-end publication tests, not a test framework.

## The publication problem, stated once

This is the accepted diagnosis; it is repeated here only to define the fix boundary.

```text
fetch tier(s)
  -> per-tier parquet caches
  -> RUN_TIERS-filtered frame
  -> _feed_scope_filter(listings_result)      # generate_listings.py:2197
  -> write_listings_json(...)                 # readme_generation.py:121
  -> independent workflow commit              # update-*.yml
```

`snapshots.merge()` is not called by `generate_listings.py`; the only non-test callers are the shadow publisher's `collect`/`eligible` paths (`Listings/shadow_publish.py:86-87`). `snapshots.record("jobhive", ...)` writes a sidecar for the live fetch (`generate_listings.py:2196`), and `snapshots.write_report()` is called at `generate_listings.py:2454`, but the published checkout contains neither `pages/snapshots.json` nor `Listings/cache/snapshots/`. That means the snapshot ledger is not yet an artifact a consumer or operator can rely on.

The smallest correction is not "write a better dedupe." It is:

1. Every source writes a validated snapshot plus sidecar.
2. The publisher reads **all eligible** snapshots in precedence order; it never reads `RUN_TIERS`.
3. The publisher writes one feed through an atomic replace after validation.
4. A manifest records the counts and hashes of inputs and output.
5. The previous good artifact remains available until the new one passes.

## Tooling assessment

The existing stack is Python, pandas/DuckDB, GitHub Actions, parquet caches, and JSON artifacts. That is appropriate for the current data volume and team size. The question is which additions buy measurable reliability now.

| Option | Decision now | Reason | Revisit trigger |
|---|---|---|---|
| **GitHub Actions** | **Keep** | Already runs the schedules, has the caches and checkout, and needs no new control plane. Fix the workflow contract rather than replace the runner. | A run routinely exceeds the job limit, or backfills/lineage become routine. |
| **Dagster** | **Do not adopt** | Asset graph, lineage, and backfills are real benefits, but migrating five workflows and a Python pipeline is a large change with no measured failure it fixes. The current failure is a publisher bug, not an orchestrator gap. | More than roughly 20 independently scheduled asset groups, multi-environment backfills, or a need for cross-run lineage. |
| **Prefect** | **Do not adopt** | Same migration cost as Dagster, with less benefit at this scale. The retry behavior that matters is already in `http_get`. | Same as Dagster; choose one orchestrator only after a measured trigger. |
| **Great Expectations** | **Do not adopt as a platform** | A full expectation suite and data docs are heavier than the contract needed here. A small Python validator with explicit invariants catches the current failures. | A warehouse/BI layer or regulatory data-quality requirement appears. |
| **dbt** | **Do not adopt** | There is no warehouse; transforms are pandas/DuckDB in-process. dbt would add a second modeling layer and duplicate the existing SQL. | A warehouse becomes the system of record and multiple consumers need modeled tables. |
| **OpenTelemetry** | **Adopt conventions, not a collector yet** | Structured run events with `run_id`, `stage`, `source`, `status`, `rows`, `duration_ms`, and `error_class` give most of the value. An OTLP collector is infrastructure without a current multi-service need. | More than one deployed service or a real paging/on-call requirement. |
| **Apify** | **Fallback only** | It can unblock one source, but it is a paid hosted dependency and duplicates existing adapters. | One measured source gap with acceptable terms and a positive yield/cost result. |

This is deliberately conservative: no new framework is justified by the evidence in this checkout.

### The wedge

SearchTern's credible product position is:

> “The freshest, most trustworthy machine-readable feed for internships and new-grad roles, with sponsorship context and an explicit freshness contract.”

That is narrower than Simplify, Handshake, or Wellfound, and it is achievable with the data already being ingested.

### Opportunities, in order

1. **Trust before features: a freshness/verification badge.** Show `first_seen_at`, `last_verified_at`, `source`, and whether the apply link was checked. Today `verified_at` is just the run timestamp on every row, so it cannot support this claim. Fix the data before exposing a badge.
2. **A real sponsorship filter.** `visa_sponsor` is present on 1,374 rows (10.0%) as the string `"true"`, empty elsewhere. A tri-state field (`true` / `false` / `unknown`) with an evidence source is useful; the current field cannot distinguish “not a sponsor” from “no data.”
3. **A freshness contract for consumers.** Publish a manifest with `generated_at`, `feed_age_seconds`, row count, and source ages. This is more valuable than a “15-minute” marketing claim that the current priority feed cannot support (it was 55.2 hours quiet at review).
4. **Saved searches and alerts.** Table stakes for a job product, but only after publication is reliable. Building alerts on a feed that can lose 60% of its sources is negative value.
5. **A stable public API/MCP surface.** The current MCP server loads the entire feed once and caches it for the process lifetime (`Listings/searchtern_mcp.py:87-103`). Shards plus a manifest make this cheaper and fresher; an API is a later step, not a reason to add a service now.
6. **“Why this job” explanations.** Source, first-seen, last-verified, sponsorship evidence, and dedup identity. This is a trust feature, not an LLM feature.

### Product non-goals for now

- Autofill or AI application submission.
- Resume builder or application tracker.
- Employer ATS or candidate CRM.
- A social/network graph.
- Broad source expansion before the current sources survive publication.
- LLM enrichment on top of a feed with 66.8% missing first-seen timestamps.
- Any metric that implies coverage or freshness the manifest cannot prove.

## Smallest high-impact sequence

| Order | Change | Why it is first | Done when |
|---|---|---|---|
| 0 | Land the already-known identity fix and `countries/` staging | It is the precondition for the feed to exceed 13.7K; without it the publisher fix operates on the wrong data | A light run produces the expected larger set; identity regression tests pass; country pages update |
| 1 | Make publication tier-independent via eligible snapshots | Directly fixes the known “light overwrites larger feed” failure | A light run retains rows from a heavy snapshot; no source disappears merely because it was not fetched |
| 2 | Atomic writes and a count manifest | Prevents a crash from truncating the feed and ends the 9,337 / 31,434 / 13,748 contradiction | A simulated mid-write failure leaves the old feed intact; manifest counts equal the feed |
| 3 | Durable sidecars, TTL, and last-known-good | Makes “not fetched” different from “failed” and makes expiry safe | `pages/snapshots.json` exists; expired critical source serves LKG, not an empty feed |
| 4 | Move the artifact out of git; commit only the pointer | Removes the 100 MB ceiling and multi-megabyte history churn | Consumers read the manifest/release URL; the monolith is no longer committed every run |
| 5 | Data-quality contract and CI gate | Makes the feed usable for product claims | 100% required fields; tri-state booleans; no future dates; pytest runs in CI |

## What not to do

- Do not rewrite the ingestion pipeline to “fix” publication.
- Do not add Dagster, Prefect, dbt, Great Expectations, or an OTLP collector as a first move.
- Do not add Apify actors or another broad aggregator before the current sources survive a light run.
- Do not commit the 139–173 MB union to git, and do not rely on Git LFS as the consumer contract.
- Do not publish a “15-minute” or “all jobs” claim until the manifest measures it.
- Do not replace `source=jobhive` with inferred source labels; preserve provenance at write time.
- Do not make TTL expiry mean “closed.” It means “not refreshed,” which is a publication decision, not a liveness fact.
- Do not treat the current `verified_at` as proof the apply link was checked; all 13,748 rows share the run timestamp.

## Open decisions

1. **Artifact home:** GitHub Release asset first (smallest, no new vendor) versus object storage/CDN. Release assets are enough for staging and early production; a CDN is justified only after measured consumer latency or bandwidth requires it.
2. **Publisher placement:** a final step inside `generate_listings.py` versus a separate publish workflow. A separate job makes “fetch only” and “publish only” explicit and prevents independent tier jobs from writing the feed. The trade-off is one more workflow and artifact handoff.
3. **TTL versus cadence:** jobhive TTL is 24 h and light runs hourly, but the measured feed was 31 h old. Either the schedule is not running as intended or the publisher must serve last-known-good when the snapshot is expired. Both must be true before TTL is safe.
4. **Priority semantics:** is `pages/priority.json` a consumer feed or an internal fast lane? If it is a feed, it needs the same manifest and atomicity. If it is internal, stop presenting it as a publication SLA.
5. **Source of truth for counts:** the manifest should be authoritative. `run_meta`, `health`, `source_stats`, and README counts should be derived from it or explicitly labelled as run-local diagnostics.
