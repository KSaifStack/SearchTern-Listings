# Multi-industry inventory overhaul — 2026-11-11

Scope: explain the 15k → 20k → 30k → 15k inventory swings, separate opportunity
eligibility from industry classification, stop the pipeline discarding
non-technology internships, and make partial runs unable to replace a larger
valid publication. No production feed was changed from this machine; all runs
used isolated `.staging/` copies.

## 1. Root cause of the inventory swings

`pages/run_meta.json` history (40 generations, 2026-11-06 .. 11-09) shows two
stable populations, not a gradual drift:

| Runs | Published candidate rows | Which tiers ran |
|---|---:|---|
| all-tier | 28,700 – 34,531 | jobhive + freehire + breadth + ecr + ats + priority + md |
| light only | 9,337 – 9,411 | jobhive + md |
| medium only | 9,256 – 9,395 | jobhive + freehire + breadth + ecr |
| heavy only | 9,340 – 9,395 | jobhive + ats |

The "15k → 30k → 15k" swing is therefore not a scraping regression. It is five
separate defects that compound:

1. **The snapshot ledger was not in the repository.** `Listings/cache/snapshots/`
   did not exist in any commit, so every CI checkout started with parquet caches
   but no sidecars. `_load_cached` seeds them from mtime with
   `provenance_ok=false`, and `publish.build_publish_frame` then treats every
   cached source as ineligible. The union contributes nothing and the feed holds
   only what that run fetched live. Measured on the checked-out feed:
   `pages/searchtern.json` was **13,748 rows, 100% `source=jobhive`**, while the
   caches beside it held 40,533 markdown, 21,471 ATS, 5,369 freehire and 5,106
   ECR rows.
2. **`run_meta`/README totals describe the live frame, not the publication.**
   `run_meta["total"] = len(listings_result)` is computed after the tier merge
   but before the snapshot union, so it reports 9.3k on a light run and 30k on an
   all-tier run even when both published the same feed.
3. **Closure voted from a windowed live query.** `seen_index.commit` closes entries
   whose bucket is fresh but absent from `live_keys`; for markdown and jobhive
   those keys come from 60/90-day SQL windows, so every posting older than the
   window looked "closed". The digest history shows the result: `closed=59,282`
   in one light run and `closed=31,375` in the next all-tier run.
4. **There was no floor on a shrinking publication.** `publish_generation` was
   called without `minimum_rows`, so a 9k-row frame could replace a 30k-row feed
   as long as `jobhive` was non-empty.
5. **Industry keywords decided eligibility.** `TITLE_EXCLUDE_RE` and the SQL
   `title NOT ILIKE` list vetoed `nurse`, `teacher`, `pharmacy`, `dental`,
   `veterinary`, `pastor`, `marketing intern`, `hr intern`, `human resources`,
   `sales associate`, and `sales representative`. On a multi-industry platform
   these are exactly the rows that must survive.

## 2. Changes

**Eligibility and classification are now separate.**

* `Listings/taxonomy.py` — sixteen published career families with industry,
  subcategory, cross-family membership, confidence, and a reason. Unknown titles
  fall back to `Other Professional` (`confidence="low"`,
  `reason="no_keyword_match"`); they are never dropped for being unclassifiable.
* `opportunity_eligibility()` refuses only non-career artefacts
  (`internal only`, `internal audit`, `internal medicine`) and senior/executive
  titles with no intern/new-grad marker. It has no industry vocabulary.
* `classify.TITLE_EXCLUDE_RE` / `TITLE_EXCLUDE_TERMS` lost every profession term;
  `LISTINGS_ONLY_EXCLUSIONS` no longer drops `marketing intern`, `hr intern`, or
  `human resources`. A new `Government/Public Service` subcategory exists so
  public-sector roles are not filed as Legal.
* Every published record now carries `career_family`, `industry`,
  `career_families`, `career_confidence`, `career_reason`, plus the legacy
  `category` (unchanged vocabulary) for existing consumers.

**Publication safety.**

* `prepare_listings_json` refuses a publication smaller than 60% of the previous
  generation's searchtern row count once that generation had ≥500 rows
  (`SEARCHTERN_MIN_RETAINED`, `0` disables). The previous feed, manifest and
  LKG stay byte-identical; the run reports the retention floor.
* `pages/coverage.json` is written inside the same atomic transaction, carries
  the generation id and published counts, and is included in the LKG surface and
  `audit()` so coverage can never describe a different generation than the feed.

**Freshness.**

* Rows now carry `source_posted_at`, `first_seen_at`, `last_seen_at`,
  `last_verified_at`, `closed_at`, and `verification_status`
  (`verified` = the source snapshot was re-fetched inside its TTL this run;
  `observed` = republished from a still-valid snapshot).
* The general feed no longer deletes rows by age (`mirror_max_age_days=None`);
  age only bounded the technology subset, which keeps its documented 60-day
  window for compatibility. TTL expiry removes rows from a feed and still never
  stamps them closed.

## 8. Remaining limitations

* **No full all-tier crawl was completed in this pass.** A bounded light run was
  attempted twice and exceeded its budget during enrichment; the publication
  path was therefore validated over caches. A deployed all-tier cycle is still
  required to refresh the ledger and measure verified-active share.
* **The ledger must persist.** CI commits `Listings/cache/`, so sidecars written
  by the next real run are carried forward. Until that run happens, every cache
  on a fresh checkout is still seeded and ineligible; the retention floor is what
  prevents that state from shrinking the feed.
* **Closure inputs remain windowed.** Postings older than the 60/90-day SQL
  window are absent from `live_keys` and can still be counted closed on a run
  whose bucket refreshed. The reviewed closure rule needs the window to be
  reported alongside the vote; it is not changed here.
* **`freehire` is technology-only**, by its own API parameter.
* **EchoJobs is IP-blocked** from this host; source health reports it degraded.
* **Frontend consumption was not exercised.** `searchtern.json` is the
  all-industry feed and now carries `career_family`/`industry` per record;
  whether the deployed client exposes those filters is outside this repository.
